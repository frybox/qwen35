设备：RTX 4090 D（24 GB）。两侧都是 **CUDA 全 offload**，`--threads 1` / `-t 1`，
prompt `天空为什么是蓝色的？`（17 tok），生成 48 tok。每个变体两侧各跑 2 次，取 decode 较优的一次。

- 本仓库：`zig-out/bin/qwen35 run <gguf> ... -n 48 --threads 1 --backend cuda`
- llama.cpp：`/mnt/llm-dev/llama.cpp194/build/bin/llama-cli -m <gguf> -p ... -n 48 -t 1 -v`

  `llama-b10707-cuda` 缺 `libnccl.so.2` 且启动即 segfault，两者都不能用于 CUDA 对比。）

## 汇总

| 指标 | qwen35 | llama.cpp CUDA |
|---|---|---|
| decode 几何平均 | **124.90** | **382.37** |

**decode 比值几何平均 = 0.327×**（qwen35 是 llama.cpp 的 1/3）。

**qwen35 落后最多的 5 个格式**（decode 比）：

| 格式 | 比值 |
|---|---|
| BF16 | 0.110 |
| UD-Q8_K_XL | 0.164 |
| UD-Q6_K_XL | 0.265 |
| UD-Q4_K_XL | 0.272 |
| UD-Q5_K_XL | 0.274 |

**qwen35 领先最多的 3 个格式**：Q4_0 0.416、UD-Q2_K_XL 0.416、Q3_K_M 0.411 ——
即"最接近但仍落后 2.4×"的三个，没有任何一个格式 qwen35 领先。

反过来在 **prefill** 上 qwen35 全面领先：几何平均 337.3 vs 184.0（1.83×），
**22/22 个格式比值都 >1**，范围从 Q8_0 的 1.08× 到 UD-Q3_K_XL / UD-IQ3_XXS 并列的 3.30×。
领先幅度与每权重比特数不单调：最大的 BF16 有 2.13×、最小的 Q8_0 只有 1.08×，
夹在中间的 4 比特档从 1.44× 到 3.30× 都有。

## 离散度

22 个变体 × 2 侧各 2 次，**没有任何一对的 decode 差异超过 10%**，不需要第三次测量。
独立抽查 Q4_K_M 三次：qwen35 153.17 / 156.13 / 156.82，llama.cpp 389.75 / 400.53 / 400.58，
与表中数值一致。

## 失败/异常

**22/22 变体、两侧全部成功，无失败、无 fallback 警告。**
（BF16 两侧都是各自最慢的格式，已确认 qwen35 侧无 CPU fallback 日志、
llama.cpp 侧 `offloaded 25/25 layers to GPU`，数字是真实的 GPU 结果。）

## 两条可复算的客观观察

1. **prefill 领先、decode 落后，是两条不同的路径**。prefill 是 17 tok 的批量
   prefill，qwen35 走 K-token 批量 chunk；decode 是逐 token 的 matvec。
   prefill 比值 1.83×、decode 比值 0.327×，两者方向相反，说明差距不在 kernel 覆盖度
   （那会两边一起慢），而在**逐 token 路径的固定开销**。
2. **差距对格式不敏感（BF16 除外）**：去掉 BF16 与 UD-Q8_K_XL 两个极端后，
   其余 20 个格式的 decode 比值集中在 0.265–0.416，跨度 1.57×，
   而 llama.cpp 侧这些格式的 decode 从 355.87 到 408.60（跨度 1.15×）也基本持平。
   对照观察 1：如果 qwen35 的 decode 是受权重带宽支配，比值应随每权重比特数
   单调变化；实测没有这个趋势。两个极端（BF16 0.110、UD-Q8_K_XL 0.164）
   都落在"权重最大"的一侧，与观察 1 的固定开销解释方向一致，但仅凭本表
   不足以断言因果，需要单独 profile。
